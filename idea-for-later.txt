

# FPGA DPLL Design and Conversion


Conceptually, a Digital Phase-Locked Loop (DPLL) is a natural fit for
an FPGA, which excels at determinism and parallel processing. However,
a direct architectural translation of `dpll_thread` would map poorly
to hardware because the software heavily relies on floating-point
arithmetic, threaded message queues, and computationally expensive
standard deviation calculations.

Here are the primary design considerations and architectural changes
required to map this to an FPGA.

### Phase Detection and Time Stamping

The software uses a queued message passing system
(`thread_slinger_queue`) to deliver timestamp objects from the
reference and oscillator threads. In an FPGA, event queueing is
unnecessary and overly complex for this task.

* **Change:** Use hardware time-to-digital capture registers. Run a
    wide, fast free-running counter driven by a high-speed system
    clock. When the external reference clock or oscillator clock
    triggers a rising edge, immediately capture the current counter
    value into dedicated registers.
* **Phase Error:** Subtract the captured oscillator timestamp from the
    reference timestamp to generate a discrete, integer-based phase
    error.

### Arithmetic and PI Controller

The `dpll_thread` calculates `accum_err` and `prop_adjust` using
64-bit `double` types and floating-point coefficients, such as $K_p =
1.055244 \times 10^{-2}$. Implementing floating-point math in an FPGA
consumes massive amounts of DSP slices and logic elements.

* **Change:** Convert entirely to fixed-point integer
    arithmetic. Multiply the $K_p$ and $K_i$ parameters by a large
    power of two (e.g., $2^{32}$) to create integer constants.
* **Implementation:** The calculation becomes $P = \text{error} \times
    K_{p\_int}$ and $I = I + (\text{error} \times K_{i\_int})$. A
    simple arithmetic right-shift operation can then divide the result
    back down to the integer scale required for the DAC.

### Lock Detection and Stage Progression

To determine lock state and stage progression, the code uses a
100-sample history (`stats_history<double, 100>`) to compute the
standard deviation of recent adjustments (`ad_sd`). Calculating a true
standard deviation requires division and square roots, which are
highly inefficient in hardware.

* **Change:** Replace the standard deviation calculation with a
    hardware-friendly metric like Mean Absolute Deviation (MAD), or
    use a simple Infinite Impulse Response (IIR) leaky integrator to
    track the magnitude of the phase error over time: $\text{Avg}_{n}
    = \text{Avg}_{n-1} - (\text{Avg}_{n-1} \gg K) +
    \vert{}\text{error}\vert{}$.
* **Thresholding:** Compare this simplified integer metric against
    statically scaled `lock_thresh` limits to drive the stage
    progression state machine.



### Oscillator Control

The original thread updates an internal variable via `osc_interval =
INTERVAL + adjust`.

* **Change:** The PI controller's integer output must be offset and
    mapped to the specific bit-width of your DAC (e.g., a 16-bit
    unsigned integer).
* **Output:** This mapped value is then transmitted to the DAC over a
    hardware interface like SPI or I2C to physically warp the
    voltage-controlled oscillator.










# A DPLL that dynamically scales based on error statistics



// Standard deviation assumes noise is white and Gaussian. Clock
// wander and scheduling delays often present as random walk or
// flicker noise, which standard deviation fails to accurately
// characterize over time.

// Allan Variance: Instead of tracking the standard deviation of
// proportional adjustments, track the overlapping Allan Variance (or
// Time Deviation). This metric is designed specifically for clock
// synchronization because it differentiates between high-frequency
// jitter (scheduling delays) and low-frequency drift (actual
// oscillator error). The phase data equation is:

// $$\sigma_x^2(\tau) = \frac{1}{2(N-2)\tau^2} \sum_{i=1}^{N-2} (x_{i+2} - 2x_{i+1} + x_i)^2$$

// Outlier Rejection (Median Filtering): Because WSL injects massive,
// intermittent latency spikes, feeding these directly into the PI
// controller destabilizes the loop. Implement a sliding window median
// filter on the raw phase_err before it reaches the controller.

// Continuous Gain Scheduling: Calculate an instantaneous noise
// envelope and use it to dynamically scale your loop bandwidth
// ($\omega_n$).

// Error-Driven Scaling: When the phase error derivative (change in
// error) is small but the absolute error is high, the loop can widen
// its bandwidth. When the noise floor increases (like in WSL), the
// loop can automatically narrow to filter it out.

// Sliding window to calculate noise floor
double noise_envelope = calculate_variance(sd_history, sd_got);

// Dynamically scale parameters based on the current noise floor rather than stages
// Base Kp and Ki would be your tightest desired bandwidth (e.g., your Stage 5)
double adaptive_multiplier = 1.0;

if (noise_envelope > BASE_NOISE_FLOOR) {
    // Widen bandwidth linearly or logarithmically as noise/error increases
    adaptive_multiplier = (noise_envelope / BASE_NOISE_FLOOR);
}

// Cap the multiplier to prevent instability
if (adaptive_multiplier > MAX_MULTIPLIER) adaptive_multiplier = MAX_MULTIPLIER;

double current_kp = BASE_KP * adaptive_multiplier;
double current_ki = BASE_KI * adaptive_multiplier;

accum_err  += phase_err * current_ki;
prop_adjust = phase_err * current_kp;
